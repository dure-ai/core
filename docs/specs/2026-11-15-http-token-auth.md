# HTTP 전송과 토큰 인증 설계 (초안)

- 작성: 한재혁, 2026-11-15. 2026-11-22 개정.
- 상태: 초안. [결정 필요] 표시는 리뷰에서 정한다.
- 근거: 1차 발표 피드백("세션에 신원을 맡길 수 없을 때 매 recall에서 범위를 어떻게 인증하나"), R5 조사, 허진수 "권한 방향" 문서(11-19 초안 v2, 11-21 리뷰 반영)
- 시기: 2차 검증(11-28) 뒤 착수. 권한 방향 문서의 **단계 2**(로드맵 P1-12)를 구현하기 위한 설계다.

**11-22 개정에서 바뀐 것**: 권한 방향 문서에 맞췄다. (1) 범위를 personal·team으로 줄였다. org와 여러 팀 소속은 v0.2(단계 3)로 넘겼다. (2) 팀 소속의 기본 출처를 토큰 `groups` claim에서 **설정 파일**로 바꾸고, claim은 선택으로 남겼다. (3) 선언 파일을 YAML에서 TOML로 바꿨다. (4) 회수 지연이 줄어드는 범위(팀 이동)와 줄지 않는 범위(퇴사)를 나눠 적었다. (5) `human` 판정은 토큰에서 나오지 않는다고 적었다. (6) 간이 정적 토큰 모드를 더했다. (7) 가시성 규칙(`access.py`)을 바꾸지 않으므로 작업 단위에서 그 항목을 뺐다.

## 1. 목표와 범위

**목표**
- 서버 하나가 여러 사람의 요청을 받을 수 있게 한다(Streamable HTTP).
- 호출자는 요청마다 토큰으로 확인한다. 볼 수 있는 범위는 지금 규칙(personal은 본인, team은 같은 팀)을 그대로 쓰고, 팀 소속은 서버의 관계 출처에서 읽는다.
- MCP 명세 2026-07-28(무상태 코어)로 붙는 클라이언트를 지원한다.

**하지 않는 것**
- 계약(`Event`, `Caller`, `Scope`, 엔진 포트) 변경. 이 단계는 계약 변경이 없다. 엔진과 하네스는 그대로 둔다.
- org 범위와 여러 팀 소속. 계약에는 `org` 값이 남아 있으나 v0.1에서는 쓰지 않는다(권한 방향 문서 1장). 여러 팀 소속·프로젝트는 "볼 수 있는 컨테이너 집합"으로 v0.2에서 계약과 함께 바꾼다(7장).
- 토큰 발급 서버를 직접 만드는 것. 발급은 외부 IdP가 맡는다(4-1).
- 외부 권한 엔진(SpiceDB, OpenFGA) 도입. 확장점만 남긴다(3-5).
- stdio 서버 제거. 로컬 개인·팀별 배포는 지금처럼 환경 변수 신원으로 남긴다.
- 팀 공유 저장소 선택. PostgreSQL 저장소는 core#25(P1-8)가 맡고, v0.1에 무엇을 쓸지는 권한 방향 문서 8장의 결정을 따른다. 이 설계는 저장소와 무관하게 쓴다.

**성공 기준**
- 토큰 없는 요청 401, 권한 부족 403(`insufficient_scope`), 다른 서버 앞으로 발급된 토큰 거절.
- 사용자 A의 토큰으로 사용자 B의 personal 기록이, 팀 X 소속이 아닌 사람에게 팀 X 기록이 recall되지 않는다(기존 누출 테스트를 HTTP 경로에서 다시 통과).
- 에이전트가 도구 인자(`repo`, `scope`, `signal`)로 권한을 넓힐 수 없다.
- 설정 파일에서 팀을 옮긴 사람은 캐시 주기(4-3) 안에 옛 팀 기록을 볼 수 없다.
- 관계 출처를 읽지 못하면 요청을 거절한다(닫힌 쪽으로 실패).
- stdio 경로의 기존 테스트가 그대로 통과한다.

## 2. 지금 구조 (2026-11-22 main 기준)

- `server.py`의 `Service`가 `user`, `team`, `session`, `agent`, `repo`를 **생성 시점에 인스턴스 값으로** 들고, 서버 전체에 `get_service()` 하나만 있다. 프로세스 하나 = 사용자 하나 = 세션 하나다.
- 범위 정책은 설정된 저장소(`CORTEX_REPO`)로 고른다(`record`, `report_outcome`, `_outcome_default`). 도구 인자 `repo`는 근거 위치만 바꾸고 정책은 못 바꾼다. 이 값을 믿을 수 있는 이유는 서버를 띄운 사람이 정했기 때문이다.
- `report_outcome`은 에이전트가 넘긴 `signal`을 버리고 `self`로 저장한다(core#10). `test`·`human` 신호가 들어오는 MCP 밖 경로는 아직 없다(core#12 초안).
- 가시성 규칙은 `access.py` 한 곳에 있고, 저장소 질의·결정 검증·handoff 필터가 모두 이것을 쓴다. personal은 "기록한 사람이 나", team은 "같은 팀"(`Caller.team`과 이벤트의 `team` 비교), 지식은 "근거 기록을 모두 볼 수 있어야 보임"이다. 사람은 팀 하나에 속한다.
- 환경 변수 신원은 보안 경계가 아니다. 에이전트는 바꿀 수 없지만 사람은 `CORTEX_USER`를 바꾸거나 DB를 직접 열 수 있다. 사람 단위의 경계는 이 설계(토큰)와 DB 접근 통제에서 생긴다.
- `session`은 서버 시작 때 만든 uuid다. 런타임은 recall 이벤트에 남기고, 지금 core 엔진 중 이 값을 읽는 엔진은 없다. 계약은 독립 출처 단위를 `user` 또는 `(user, session)`으로 열어 두었다(contract.md 미결 항목).
- 전송은 `mcp.run()`(stdio)뿐이다. SDK(`mcp` 2.3.0)는 `MCPServer(token_verifier=..., auth=AuthSettings(...))`, `run(transport="streamable-http")`, 요청별 `get_access_token()`을 제공한다(로컬에서 API 확인).

## 3. 설계

### 3-1. 권한 모델

이 단계의 판단은 둘뿐이다(권한 방향 문서 5장).

| 질문 | 무엇으로 | 출처 |
|---|---|---|
| 이 작업을 해도 되나 | 토큰 scope(3-3) | 토큰 |
| 이 기억을 볼 수 있나 | 팀 소속 + 지금의 personal·team 규칙 | 관계 출처(3-2) |

관계로 쓰면 다음과 같다. v0.2에서 관계(ReBAC)를 넓힐 때 같은 이름을 쓴다.

| 관계 | 쓰임 | 출처 |
|---|---|---|
| 사람 `member` 팀 (하나) | team 범위 가시성, 쓰기 팀 | 설정 파일(기본) 또는 토큰 claim(선택) |
| 팀 `owns` 저장소 | 도구 인자 `repo` 확인 | 설정 파일 |
| 저장소 기본 범위 | 쓰기 범위 정책(지금 `CORTEX_REPO_SCOPES`) | 설정 파일 |
| 지식 `derived_from` 기록 | 근거를 모두 볼 수 있어야 보임(지금 handoff 필터 그대로) | 이벤트 로그 |

v0.2로 미룬 관계: 팀 `part_of` 조직(org), 사람 `member` 여러 팀, 프로젝트, 사람 `admin` 팀(4-4).

다른 방식과의 역할 분담:
- RBAC: 따로 두지 않는다. 토큰 scope가 거친 역할을 맡고, 나머지는 관계로 표현한다.
- ABAC: 지금처럼 기억의 `conditions`와 저장소별 기본 범위에 쓴다. 기밀 등급(`classification` ≤ `clearance`)은 고객 요구가 생길 때 더한다(권한 방향 문서 단계 4).
- PBAC(OPA, Cedar 같은 정책 엔진): 쓰지 않는다. 필요하면 3-5의 확장점으로 연다.

### 3-2. 관계 출처: 설정 파일이 기본

**설정 파일(`relations.toml`)**
- 사람 → 팀, 팀 → 저장소, 저장소 기본 범위를 둔다. 표준 라이브러리 `tomllib`로 읽어 의존성이 늘지 않는다.

  ```toml
  [teams.payments]
  members = ["alice@acme.com", "bob@acme.com"]
  repos = ["acme/api", "acme/billing-*"]

  [teams.platform]
  members = ["carol@acme.com"]
  repos = ["acme/infra"]

  [repo_defaults]        # 지금 CORTEX_REPO_SCOPES와 같은 뜻
  "acme/handbook" = "team"
  "acme/*" = "team"
  ```
- `members`의 값은 토큰의 `subject`(또는 4-1에서 정할 사용자 claim)와 같은 값이다.
- 한 사람이 두 팀에 들어 있으면 서버가 시작하지 않는다. 여러 팀 소속은 v0.2다.
- **갱신 책임**: 팀 관리자가 팀원이 바뀔 때 고친다. 파일을 git으로 관리하면 PR과 리뷰를 거치고 변경 이력이 남는다. 이 파일은 보안 설정이므로 변경 권한을 CODEOWNERS 등으로 따로 지킨다.
- **다시 읽기**: 서버는 캐시 주기(4-3, 예: 60초)마다 파일이 바뀌었는지 보고 다시 읽는다. 재시작이 필요 없다.
- **잘못된 파일**: 시작 때 검증에 실패하면(없는 팀, 겹치는 저장소 패턴, 두 팀에 든 사람) 시작하지 않는다. 실행 중 다시 읽다 실패하면 [제안] 마지막으로 성공한 내용을 그대로 쓰고 오류를 남긴다. 파일 자체를 읽을 수 없게 되면 요청을 거절한다.
- 이유: 단계 2에서는 한 사람이 한 팀에 속하므로 파일 하나로 충분하고, IdP 설정 없이도 돌아간다. 팀 이동이 토큰 수명과 상관없이 캐시 주기 안에 반영된다.

**토큰 claim(선택)**
- IdP가 팀 정보를 claim으로 주는 조직은 설정에서 claim 어댑터를 켤 수 있다. 이때도 claim 값과 팀 이름의 매핑, 저장소 소유·기본 범위는 설정 파일에 둔다.
- claim으로 팀을 받으면 팀 이동 반영이 토큰 수명만큼 늦는다. 그래서 기본값으로 두지 않는다.

**회수 지연이 줄어드는 범위**
- 줄어드는 것은 **팀 이동**이다. 설정 파일을 고치면 캐시 주기 안에 옛 팀 기록이 안 보인다.
- **퇴사**는 줄지 않는다. 설정 파일에서 지워도 그 사람의 personal 기록 접근은 토큰이 만료될 때까지(최대 토큰 수명) 남는다. 더 빨리 끊으려면 IdP의 토큰 폐기나 더 짧은 토큰 수명이 필요하다(4-2).

**stdio(로컬)**
- 지금처럼 환경 변수(`CORTEX_USER`, `CORTEX_TEAM`, `CORTEX_REPO`)로 신원을 정한다. 설정 파일이 있으면 저장소 기본 범위를 거기서 읽는다.

**대안(채택하지 않음, 확장점으로 남김):** IdP는 SCIM으로, GitHub 팀·저장소 권한은 API로 서버 DB의 관계 테이블에 동기화하는 방식. 그룹 수 제한이 없고 감사·외부 ReBAC 엔진 연결이 쉽지만, IdP·GitHub마다 동기화 코드와 실패 감시가 필요하고, 동기화가 멈추면 퇴사자가 계속 볼 수 있으며, 작은 팀에게 설치 부담이 크다. 디렉터리 동기화는 단계 3 이후에 다시 본다.

### 3-3. 신원과 권한: 토큰

- `TokenVerifier.verify_token(token) -> AccessToken | None`을 구현한다. 서명(JWKS), 만료, 발급자(`iss`), 대상(`aud`/`resource`가 이 서버의 URI)을 확인한다.
- 토큰에서 읽는 것은 셋이다: **누구인가**(`subject` → user), **어디까지 쓸 수 있나**(OAuth scope), **사람인가 서비스인가**(4-1에서 정할 토큰 종류 표시). 팀은 관계 출처에서 읽는다(3-2).
- 신원은 토큰에서만 읽는다. `clientInfo`(클라이언트가 스스로 밝히는 값), 도구 인자, 헤더는 신원으로 쓰지 않는다. 받은 토큰을 다른 서비스에 넘기지 않는다(명세의 passthrough 금지).
- 토큰 수명은 짧게 둔다(예: 1시간, 4-2). 팀 소속을 관계 출처에서 읽으므로 토큰 수명은 인증과 퇴사자의 본인 기록 접근에만 영향을 준다.

| 토큰 scope | 허용 |
|---|---|
| `memory:read` | `recall` |
| `memory:write:personal` | personal 범위 기록·결과 보고 |
| `memory:write:team` | team 범위까지 |

- 도구 호출 자체에 필요한 scope가 없으면 403 `insufficient_scope`.
- 쓰기 범위는 `min(저장소 기본 범위, 토큰 상한)`이고, 에이전트는 그 안에서 좁히기만 한다(지금 `_narrow`와 같은 규칙). 범위만 부족하면 거절하지 않고 좁혀서 저장하고 응답의 `scope`로 알린다. 성공하던 요청을 실패시키지 않는다.

**판정 주체(`signal`)**
- 토큰 종류에서 정한다. 사람·에이전트 토큰은 `self`, CI·테스트 러너의 서비스 토큰은 `test`. 에이전트가 도구 인자로 `signal`을 바꿀 수 없다는 지금 원칙(core#10)을 그대로 둔다.
- `human`은 토큰으로는 나오지 않는다. Claude Code 같은 클라이언트는 사람의 토큰으로 요청을 보내므로, 서버에서 사람과 에이전트가 같은 토큰으로 보인다. `human` 판정은 계약에 적힌 관리 CLI나 Git 훅 같은 별도 경로로만 들어온다.

**간이 정적 토큰 모드 [제안]**
- IdP가 없는 작은 팀을 위해, 사람마다 미리 나눠 준 무작위 토큰을 설정 파일에서 사용자로 매핑한다. 파일에는 토큰 값이 아니라 해시(SHA-256)만 둔다.
- 개발·소규모용이다. 운영 기본값은 OAuth다. 이 모드에서는 토큰 만료가 없으므로 퇴사자는 설정 파일에서 지우는 순간 끊긴다.

### 3-4. 요청 처리: `Service`를 요청 단위로

요청마다 다음 순서로 `Principal`과 `Caller`를 만든다.

1. 토큰 확인 → user, 쓰기 상한, 토큰 종류.
2. **팀 찾기:** 관계 출처에서 user의 팀을 읽는다. 팀이 없으면 personal만 쓸 수 있다(team 기록 조회도 없음).
3. **저장소 확인:** 도구 인자 `repo`가 그 팀이 `owns`하는 저장소면 그 저장소의 기본 범위를 쓴다. 아니면 근거 위치로만 남기고 범위 정책은 기본값(personal)을 쓴다. 다른 팀 저장소 이름을 대서 범위를 넓힐 수 없다.
4. `Caller(user, team, session, at, agent, repo, context)`를 만든다. 계약 모양은 그대로다.

- `Service`에서 신원 값을 빼고 요청마다 `Principal`을 받는다. stdio는 환경 변수로 `Principal`을 한 번 만들고(지금과 같은 동작), HTTP는 요청마다 만든다.
- `Runtime`, 저장소, 엔진은 프로세스에 하나로 공유한다.
- **가시성 규칙은 바꾸지 않는다.** 한 사람이 한 팀이므로 `Caller.team` 하나로 지금 `access.py`와 저장소 질의가 그대로 맞다. 바뀌는 곳은 `Caller`를 만드는 서버 코드뿐이다.

### 3-5. 확장점: `RelationSource`

관계 해석은 인터페이스 하나로 감싼다.

```python
class RelationSource(Protocol):
    def team_of(self, principal: Principal) -> str | None: ...
    def owners_of(self, repo: str) -> frozenset[str]: ...
    def repo_default(self, repo: str | None) -> Scope: ...
```

- 기본 구현: 설정 파일(3-2). 선택 구현: 토큰 claim 어댑터.
- 나중 구현: SCIM·GitHub 동기화, 외부 ReBAC 엔진(SpiceDB, OpenFGA) 어댑터.
- v0.2에서 여러 팀 소속·프로젝트가 생기면 `team_of`가 "볼 수 있는 컨테이너 집합"을 돌려주도록 바뀐다. 그때는 `Caller`와 `access.py`가 함께 바뀌므로 계약 변경이다(7장).

### 3-6. 세션

2026-07-28에는 프로토콜 세션이 없고, 서버 세션도 두지 않는다. `Caller.session`은 "어느 작업 세션의 기록인가"라는 꼬리표이고 인증 세션이 아니다. 계약 필드라 값은 있어야 한다.
- 클라이언트가 요청 `_meta`로 작업 id를 넘기면 그것을 쓰고, 없으면 요청마다 새로 만든다. 신원과 무관한 기록용 값이다.
- 독립 출처 단위는 `user`로 두는 쪽이 안전하다(같은 사람이 세션을 바꿔 여러 번 쓰는 것을 막는다). 계약 미결 항목과 함께 정한다.

### 3-7. 동시성

HTTP 서버는 한 프로세스에서 여러 요청을 동시에 처리한다. core#25는 엔진의 `observe`와 임베딩을 쓰기 트랜잭션 밖으로 빼고 커밋 시점에 검사한다. 두 프로세스가 겨루면 같은 이벤트에 `observe`가 두 번 돌 수 있고 결과는 하나만 커밋된다고 적혀 있다. 한 프로세스 안의 동시 요청에서도 같은지, `Runtime`의 실패 횟수와 `skipped` 목록(프로세스 단위 상태)이 안전한지는 확인하지 않았다. 구현 첫 단계에서 동시 호출 테스트로 확인한다.

## 4. 결정할 것

**4-1. 토큰 발급자와 토큰 종류** — 외부 IdP의 JWT를 JWKS로 검증하는 구조로 짜고, 개발·시연은 테스트용 발급기로 한다. 사용자 식별 claim(`sub` 또는 `email`)과 서비스 토큰을 구별하는 표시(별도 scope `memory:signal:test` 또는 client credentials 여부)를 정한다. [제안, 리뷰에서 확정]

**4-2. 토큰 수명** — 1시간 권장(권한 방향 문서 8장). 팀 이동에는 영향이 없고, 인증과 퇴사자의 본인 기록 접근에만 영향을 준다. [제안]

**4-3. 관계 캐시 주기** — 설정 파일을 다시 읽는 주기. 60초를 권장한다. 팀 이동이 반영되는 최대 지연이다. [결정 필요]

**4-4. 팀 관리자 권한** — 팀 기억을 사람이 직접 강등·정정하는 권한(`admin of team`). 이번 범위에서 빼고 회수(P1-5)와 함께 정한다. [제안]

**4-5. 독립 출처 단위** — `user`로 확정할지(3-6). 계약 미결 항목이라 진수님과 함께 정한다. [결정 필요]

**4-6. 간이 정적 토큰 모드** — 넣을지, 넣는다면 개발 전용으로 막을지(예: 설정 플래그 없이는 켜지지 않게). [결정 필요]

## 5. 영향

- **권한은 조회 시점의 관계로 계산한다.** 팀을 옮기면(캐시 주기 뒤) 옛 팀 기록이 바로 안 보인다. 본인이 그 팀에서 남긴 기록도 마찬가지다. 기록은 팀 소유로 남는다(계약의 "팀 기록은 옮길 수 없다"와 같은 원칙).
- **하네스는 영향이 없다.** 하네스는 시나리오가 `Caller`를 직접 만들어 관계 해석을 거치지 않는다.
- **누출 검사 코드는 바뀌지 않는다.** `access.py`, 저장소 질의, 결정 검증, handoff 필터는 그대로다. HTTP 경로에서 같은 누출 테스트를 다시 통과시키는 것만 더한다.
- **설정 파일이 보안 설정이 된다.** 매핑 실수가 곧 권한 실수다. 시작 때 검증하고, 잘못되면 시작하지 않는다(3-2).
- **"팀원 목록"은 설정 파일이 정본이다.** IdP와 어긋날 수 있다. IdP에서 막힌 사람은 새 토큰을 받지 못하므로 토큰 만료 뒤 끊기지만, 설정 파일에 남아 있으면 감사 화면에는 팀원으로 보인다. 디렉터리와 맞추는 일은 단계 3 이후다.

## 7. 대안과 다음 단계

**전체 구조 대안**

| 안 | 내용 | 판단 |
|---|---|---|
| 사용자마다 서버 프로세스(지금 구조 유지, 앞단 프록시가 토큰 확인) | 코드 변경이 작다 | 사용자 수만큼 프로세스. 프록시가 신원을 헤더로 넘기면 서버가 그 헤더를 믿어야 해서 신뢰 경계가 둘로 갈린다. 채택하지 않음 |
| SEP-2624 Interceptor로 정책 검사 | 정책을 서버 밖으로 | 미채택 초안이고 신원 확인을 다루지 않는다. 채택하지 않음 |
| **요청 단위 `Service` + SDK 토큰 검증 + 설정 파일 관계 출처(이 문서)** | 신원·권한 검사가 서버 안 한 지점 | 채택 |

**v0.2(단계 3)에서 할 것** (이 문서 범위 밖, 계약 변경과 팀 합의 필요)
- 여러 팀 소속·프로젝트: `Caller`가 팀 하나 대신 "볼 수 있는 컨테이너 집합"을 가진다. 가시성 조건은 "소속 컨테이너 목록에 있음"으로 넓히고 SQL로 내려보낸다.
- org 범위와 팀 간 승격.
- 승격 규칙 일반화: "지식을 읽는 사람 집합 ⊆ 각 근거를 읽는 사람 집합". 포함 관계가 분명하지 않은 컨테이너 사이는 처음에는 승격하지 않는다.
- 외부 ReBAC 엔진(OpenFGA, SpiceDB)은 `RelationSource` 구현으로 붙인다. 비교 조사는 단계 4 전에 한다.

## 8. 확인하지 못한 것

- SDK가 2026-07-28 요청(핸드셰이크 없음)을 서버 쪽에서 어떻게 처리하는지 실제로 붙여 보지 않았다.
- `AccessToken.claims`의 실제 모양(SDK 문서상 필드는 있으나 타입 미확인). 토큰 종류 표시와 claim 어댑터가 여기서 값을 읽을 수 있는지 구현 첫 단계에서 확인한다.
- 실제 클라이언트(Claude Code 등)가 HTTP MCP 서버에 OAuth로 붙는 흐름.
- core#25 머지 뒤 한 프로세스 안 동시 요청에서의 전달 동작(3-7).
